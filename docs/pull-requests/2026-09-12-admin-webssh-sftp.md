# Admin Remote Servers, WebSSH, and WebSFTP

## Title

`feat(admin): add remote servers and browser SSH/SFTP`

## Target Branch

`main`

## Summary

This change adds admin-managed remote SSH servers, SSH public-key credentials, browser-local SSH terminals, and browser-local SFTP file operations. The Server creates a one-time WebSocket ticket and brokers encrypted bytes through the existing Agent relay. It does not terminate SSH, store SSH passwords or private keys, inspect terminal output, or expose a Server-side file API.

The browser libssh2 transport now registers its custom send/receive callbacks before handshake, maps an empty WebSocket receive queue to Emscripten/WASI `EAGAIN` (`-6`) instead of the public libssh2 error code (`-37`) or Linux `EAGAIN` (`-11`), and decodes WASM heap pointers into readable SSH/SFTP error text. SFTP directory parsing also compares POSIX file-type bits exactly so regular files are no longer misclassified as symlinks.

The WebSocket byte stream now waits for `onopen` before delivering the client SSH banner. This removes a startup race where libssh2 sent its banner while the browser socket was still `CONNECTING`, causing the transport to fail and libssh2 to report `Failed getting banner`.

`@verdigris/libssh2.js@0.1.9` declares `ssh2_session_hostkey` in its TypeScript definitions but does not export the matching WASM function. The browser client now extracts the server public-key blob from the pre-encryption KEX reply and falls back to that key when the binding is unavailable, preserving interactive host-key verification without weakening SSH security.

The package also declares string arguments for functions whose actual exports use raw C pointers and lengths. The client now allocates NUL-terminated UTF-8 strings for password authentication, public-key authentication, PTY, disconnect, and SFTP paths; public-key authentication uses the actual seven-argument ABI. The host-key confirmation dialog renders the fingerprint as a wrapped standalone code block instead of embedding a long value in a normal sentence.

The ninth round adds lrzsz (ZMODEM) transfers inside the browser terminal and stored credential secrets that let WebSSH/SFTP authenticate without a dialog. Credentials now come in two types, `ssh_public_key` (optionally storing the private key and passphrase) and `password`; secrets are sealed with the existing AES-256-GCM `auth.SecretStore` and delivered to the owner's browser exactly once at session creation. Schema expands from v12 to v13 with four nullable `credentials` columns.

## User Impact

- Administrators and authorized users can maintain remote SSH server records and SSH public-key credentials.
- Remote-server lists show joined Agent and credential display names plus Agent online state.
- SSH passwords are entered per session and retained only in browser memory.
- WebSSH verifies the SSH host-key fingerprint interactively before continuing.
- WebSFTP supports directory browsing, upload, download, rename, delete, and progress display over the same authenticated SSH connection.
- Single-file browser transfers are capped at 1 GiB before transfer begins.
- The 远程服务器 page lists the caller's own active SSH sessions and can disconnect one, which releases the active-session quota immediately instead of waiting for `session_ttl`.
- A terminal whose remote shell exited prints the remote exit code or terminating signal and offers 重新连接 back to the matching server's authentication dialog.
- Empty lists render the normal Element Plus empty illustration on every route instead of an unstyled oversized graphic.
- 密钥管理 offers two credential types; an `ssh_public_key` credential can additionally store its private key, and a `password` credential stores only a password. Both are encrypted at rest and reported as 已保存 / 未保存.
- A remote server bound to a credential that holds a secret is tagged 自动认证, and clicking SSH 连接 or SFTP 文件 enters directly without the password dialog. Without a usable secret the manual dialog still appears, so nothing regresses for existing rows.
- The terminal supports lrzsz: `sz <file>` downloads to the browser and `rz` opens a multi-file picker and uploads to the remote working directory. A transfer panel shows direction, name, progress and 取消传输, and keystrokes are not forwarded to the remote while a transfer runs.

## API / Schema / Configuration Impact

- API adds credential CRUD and one-time private-key extraction, remote-server CRUD, and WebSSH ticket/session operations under `/api/v1`.
- API adds `GET /api/v1/ssh-sessions`, a cursor-paged list of the caller's own active WebSSH sessions; owner scope is enforced in the service and administrators also see only their own sessions.
- Schema expands from v11 to v12 with `credentials`, `remote_servers`, and `webssh_sessions`; no existing table is modified.
- Schema expands from v12 to v13 with four nullable `credentials` columns (`secret_ciphertext`, `secret_nonce`, `secret_key_id`, `secret_version`); no existing column or index is modified and no row is rewritten.
- API extends credential create/replace/patch with a write-only `secret` object, adds `hasSecret` to credential reads, adds nullable `credentialType`/`credentialHasSecret` to remote-server reads, and adds a one-time `auth` object to the WebSSH ticket response.
- Configuration gains no new key: credential secrets reuse `TUNNELMESH_TOKEN_ENCRYPTION_KEY` / `TUNNELMESH_TOKEN_ENCRYPTION_KEY_ID`. Without them, storing a secret fails with `503` and auto-authentication degrades to the manual dialog. ZMODEM needs no server-side switch.
- Configuration adds `server.webssh` controls for enablement, ticket/session TTL, active-session limits, open/idle timeouts, and maximum WebSocket message size.
- Nginx documentation adds a long-lived, unbuffered `/ws/webssh/` location.

## Security and Authorization Impact

- Remote-server ownership and Agent policy are enforced by the service layer; handlers do not trust client-supplied ownership.
- WebSSH tickets are random, hash-stored, single-use, and time-limited.
- Browser origin validation occurs before WebSocket upgrade and ticket consumption.
- Passwords and private keys used for a browser SSH connection remain in browser memory and are never sent to the management API.
- Private-key extraction is an explicit one-time HTTPS operation: the Server parses the key in memory and returns only the public key and fingerprint; private-key material is not persisted or logged.
- Audit records contain resource IDs and result classes, not credentials, terminal bytes, or SFTP file content.
- Runtime shutdown now terminates every process-local WebSSH bridge and its Agent stream.
- Credential secrets are decrypted only for `credential.OwnerUserID`; administrators can list a credential but cannot read another user's secret.
- The decrypted secret is attached to the session-creation response after the idempotency record is written, so a replay returns the ticket without any auth material. The response carries `Cache-Control: no-store`, and the `credential.revealed` audit event records identifiers only.
- Secret ciphertext, nonce, key id and plaintext are absent from list/detail responses, audit details, logs, Prometheus, traceroute and error messages.
- ZMODEM bytes are brokered like every other WebSSH byte: the Server never parses the protocol, buffers a file, or records a file name.

A third round fixed three admin-console defects reported from production use:

- **SSH 会话创建失败 had no actionable reason.** The connect dialog replaced every rejection with the generic `remoteServers.sshFailed` string, so administrators could not tell a disabled server from an offline agent or an exhausted session quota. `writeAPIError` puts the stable identifier in `data.error` while the envelope `msg` is only the HTTP status text, so the new `web/src/views/remote-server-errors.ts` maps `APIError.domain` (`remote server is unavailable`, `remote server agent is unavailable`, `remote server credential is unavailable`, `remote server agent is offline`, `webssh active session limit reached`, `webssh username is required`, `resource is forbidden`) to localized `remoteServers.errors.*` messages, keeps an unmapped identifier readable for troubleshooting, and falls back to the generic string for non-API failures. `RemoteServers.vue` calls `sshErrorMessage(error, t)`.
- **Cross-owner WebSSH requests answered 500 instead of 403.** `writeWebSSHError` sent `ErrResourceForbidden` through `writeStorageError`, so `POST /api/v1/remote-servers/{id}/ssh-sessions`, `GET` and `DELETE /api/v1/ssh-sessions/{id}` returned `500` with the internal text `resource is forbidden`, unlike the remote-server and credential APIs which already answer `403`. `writeWebSSHError` now maps `ErrResourceForbidden` and `auth.ErrForbidden` to `403` with a non-leaking `forbidden` body.
- **The active-session limit answered 500 instead of the documented 409.** `docs/api/openapi.yaml` already promises `409: Idempotency conflict or active-session limit reached`, but the inline error fell through `writeStorageError`. No OpenAPI change was required because the implementation now matches the published contract.
- **Quota exhaustion after a Server restart.** `webssh_sessions` rows left in `active` by a previous process could never be served again, but the sweeper only reclaimed them after the 8-hour `session_ttl`, so `max_active_sessions_per_user=5` filled with dead rows and every new session failed. `WebSSHSessionRepository.CloseActiveByNode` and `WebSSHSessionService.CloseStaleLocalSessions` now close those rows once during runtime startup, before any ticket is issued, and log `webssh_stale_sessions_closed` with the affected count. The startup hook is guarded by `server.webssh.enabled` and aborts startup if the cleanup fails.
- **远程服务器 / 服务令牌 / Server 节点 tables forced a page-level horizontal scrollbar.** `.tm-page` used `display: grid` with an implicit `auto` column, so the track grew to the table's max-content width instead of the viewport. An eleventh round fixed a production report: WebSFTP uploads failed with the generic "文件传输失败" banner. - **The real production root cause: the relay's WINDOW_UPDATE mirror queue killed bulk uploads.** `handleAgentFrameGeneration` applies inbound WINDOW_UPDATE credit to `sendState` and then mirrors the frame into `controlCh` (capacity 16) for `ReadControl` consumers. The WebSSH/SFTP broker only ever calls `Read`, never `ReadControl`, so on any upload large enough to earn more than 16 updates the mirror overflowed and the dispatch failed the stream with `protocol: flow-control window exhausted`; the bridge closed, sshd saw the connection drop, and the UI reported "SFTP 通道已关闭". Evidence from a temporary bridge diagnostic: `first=protocol: flow-control window exhausted`, with the on-disk upload truncated at 768 KiB - sshd's flush lag behind the ~2 MiB of consumed credit (16 updates x 128 KiB). Downloads never hit this because Server-to-Agent credit travels through `WriteControl`, not `controlCh`, which is exactly why only uploads died. The mirror is now best-effort: when the queue is full the frame is dropped, because the authoritative credit already lives in `sendState` and `consumeSendWindow` reads it directly. Regression test `TestAgentRelayStreamSurvivesUndrainedWindowUpdates` sends 40 undrained updates and then requires `Write` to succeed; before the fix it failed with the exact production error.
- **`libssh2_sftp_write` partial returns truncated every upload (browser, pre-existing).** The session runs non-blocking, so `libssh2_sftp_write` returns the bytes consumed so far - a positive value smaller than the request, not `EAGAIN` - whenever the channel window or the tunnel stalls. `retrySFTP` only retries `EAGAIN`, and `uploadFile` treated any short write as fatal, which is precisely the generic "文件传输失败" the user saw: the bigger the file or the slower the path, the more certain the failure. The handle write now loops, feeding the unconsumed remainder at `pointer + written`, with a 5 s zero-progress stall guard so a dead tunnel surfaces as an error instead of spinning the retry loop forever.

A twelfth round fixed a production report that only reproduces on real networks: ZMODEM transfers corrupted in flight, with `rz` answering `Unhandled header: ZRPOS` / `Peer aborted session` and a finished `sz` dying with `PROTOCOL: Only thing after ZFIN should be "OO"` when the shell prompt arrived. - **Root cause: concurrent outbound writers plus the round-11 partial-write continuation.** The terminal view wires ZMODEM's synchronous `sender` callback as fire-and-forget (`void channel.write(bytes)`), and zmodem.js calls it several times per consumed chunk (ZACK, ZFIN, data subpackets), so one SSH channel routinely carries several in-flight `write()` promises. Round 11 turned each write into a loop that resends the unconsumed remainder after an `await`; under channel-window pressure - routine on a WAN link, absent on localhost - two writers' continuations interleave and the peer receives torn frames. The red unit test captured the exact wire signature: `[1,1,2,2,1,2,1,2]` instead of `[1,1,1,1,2,2,2,2]`. Torn frames explain every reported symptom: `rz` fails CRC and sends `ZRPOS` (which zmodem.js does not implement), and the browser's mangled ZFIN reply makes lrzsz `sz` exit without ever sending `OO`, so the receive session meets the prompt's `27,93` (ESC ]) where `OO` belongs.
- **Fix: one writer at a time per channel.** A new `createWriteGate()` promise chain serializes every libssh2 write-path call per channel: shell `write`/`resize`/`close` (extracted to `writeShell`/`resizeShell`/`closeShell`), and the whole SFTP surface - open, handle read/write/close, `readDirectory` (held across opendir, every readdir round and the close), `unlink`, `rmdir`, `rename`, `realpath` and `close`. A rejected task does not poison the queue; `close` queues behind in-flight operations instead of tearing the channel down mid-continuation; `writeShell` drops the remainder when `shellClosed` flips while it waits for window credit. The gate is microtask-level, adds no perceptible latency, and has no configuration.
- **The frozen-terminal symptom was a second defect.** When zmodem.js threw, `consumeFromRemote` discarded the session together with the parser's unconsumed buffer - in the post-ZFIN case that buffer is exactly the shell prompt, so the terminal sat on a blank line until the next keystroke. The catch now replays `_input_buffer` (only for a receive session past `_got_ZFIN`; a send session's leftover is peer protocol bytes) plus any chunks behind the one that threw.
- **Why E2E never caught it, and what guards it now.** On localhost the channel window never tightens, libssh2 always consumes whole buffers, and the continuation loop runs once - the interleaving window does not exist. The invariant is therefore pinned by unit tests: `never interleaves concurrent shell writes when libssh2 consumes partially`, `never interleaves an SFTP write with a concurrent SFTP request`, and `returns the parser leftover to the terminal when a receive session dies after ZFIN`. The troubleshooting guide states explicitly that a green E2E is not evidence for this fix.

- **The vendored Sentry keeps the session that threw, so the terminal dies permanently.** `zsentry.js` routes every input to `this._zsession` while it is non-null and clears it only from `_after_session_end()`, which is bound to the session's own `session_end` event. `zsession.js`'s `_consume_first()` *throws* (a string, not an `Error`) when a post-ZFIN byte is not `OO`, so `session_end` never fires and the library exposes no reset. Keystrokes keep the 5 s bound on purpose: a keystroke that cannot be written in 5 s really does mean a dead channel, and the view relies on that rejection to close the terminal. A genuine tunnel failure still surfaces, because libssh2 returns a negative code, `assertResult` throws, and the round-14 "abort the transfer, not the channel" policy applies.
- **Removing the deadline forced `close()` out of the write gate.** `close()` queued behind `shellGate`, so a single unbounded stalled writer would hang `await channel?.close()` in `closeTerminal()` forever and leak the libssh2 handles - a new failure mode that removing the deadline would otherwise have introduced. `close()` now calls `closeShell()` directly, and `closeShell()` flips `shellClosed` synchronously, which is what makes the in-flight writer unwind at its next check. To keep that safe, `retryEAGAIN` gained an optional `isCancelled` predicate and returns `0` (the "no progress" value the write loops already understand) instead of touching a handle the caller may already have freed; without it a retry attempt could land on a channel that `_ssh2_channel_free` had just released.

## Release Steps

2. Deploy the new Server with `storage.auto_init=true` so schema v11 advances to v12 and v12 advances to v13.
3. Keep `server.webssh.enabled=false` during rollout if a staged release is required.

5. Configure exact `security.allowed_origins` and the Nginx `/ws/webssh/` location.

7. Enable `server.webssh`, sign in to the admin console, and complete one SSH, one SFTP, one `sz` download and one `rz` upload smoke test.

## Rollback Steps

1. Disable `server.webssh.enabled`.
2. Close active browser sessions and roll back the application to the previous release.
3. Retain the v12 tables and the v13 `credentials.secret_*` columns; do not issue reverse DDL or manually change `schema_meta.version`. A v12 binary ignores the new columns, stored secrets simply become invisible, and browser SSH/SFTP falls back to the manual password dialog.
4. If exact schema restoration is mandatory, restore the pre-upgrade database backup.
5. Keep `TUNNELMESH_TOKEN_ENCRYPTION_KEY` unchanged across the rollback window; removing it makes stored secrets undecryptable even after upgrading again.
